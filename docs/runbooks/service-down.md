# Service Down Runbook

## Purpose

This runbook helps investigate incidents where a service is unavailable or appears down.

In IncidentHub, this runbook is attached to incidents of type:

```text
SERVICE_DOWN
```

This incident type may be generated by future heartbeat, health check or availability rules.

---

## What This Incident Means

A `SERVICE_DOWN` incident means a service is not reachable or cannot serve traffic.

This is usually more severe than high latency or isolated errors.

Possible symptoms:

- health check failing
- connection refused
- no successful requests
- service process crashed
- container not running
- readiness probe failing
- DNS or network routing failure

---

## Initial Severity

Default severity:

```text
CRITICAL
```

Use `HIGH` only if:

- the service is non-critical
- redundancy is absorbing all traffic
- there is no user impact

---

## First Response Checklist

1. Confirm affected service and environment.
2. Check whether service is reachable.
3. Check health endpoint.
4. Check container/process status.
5. Check recent deployments.
6. Check dependency failures.
7. Check infrastructure/network state.
8. Restore service availability.
9. Resolve only after sustained recovery.

## Local Service Checks

### Health endpoint

```http
GET /actuator/health
```

Expected healthy response:

```json
{
  "status": "UP"
}
```

### Docker containers

```powershell
docker ps
```

Look for:

- container missing
- container restarting
- unhealthy status
- incorrect port mapping

### Docker logs

```powershell
docker logs <container-name>
```

Look for:

- startup failures
- port binding errors
- database connection errors
- missing environment variables
- fatal exceptions

---

## Local Database Checks

If the service depends on PostgreSQL:

```powershell
docker exec -it incidenthub-postgres psql -U incidenthub -d incidenthub -c "select current_user;"
```

If this fails, the service may be down because the database is unavailable.

## Common Causes

### Process or container crash

Signs:

- service container not running
- JVM exited
- fatal stack trace
- repeated restarts

Actions:

- inspect logs
- restart service
- rollback if crash follows deployment
- fix configuration if startup failure

### Database unavailable

Signs:

- connection refused
- authentication failure
- Flyway cannot connect
- Hikari pool fails to start

Actions:

- start database
- verify port mapping
- verify credentials
- verify profile configuration

### Bad deployment

Signs:

- service down immediately after deploy
- missing config
- incompatible migration
- dependency version issue

Actions:

- rollback
- verify config
- redeploy known good version

### Port conflict

Signs:

- service fails to bind to port
- another process uses port
- local environment conflict

Actions:

- stop conflicting process
- change port configuration
- restart service

### Network or DNS issue

Signs:

- service runs but cannot be reached
- name resolution failures
- connection timeout

Actions:

- check network
- check DNS/service discovery
- verify ingress/routing

---

## Mitigation Options

### Restart service

Use if crash is transient and no bad deployment is suspected.

### Roll back

Use if issue started after a deployment.

### Start missing dependency

Use if dependency such as database or queue is down.

### Scale replacement instances

Use if only some instances are down.

### Reroute traffic

Use if one availability zone, node or instance group is affected.

---

## Escalation Criteria

Escalate immediately if:

- production service is unavailable
- no healthy replicas remain
- service is part of checkout/payment flow
- restart does not restore service
- root cause is infrastructure-wide

Escalate to:

- service owner
- platform team
- database team if DB-related
- incident commander for critical production outage

---

## Resolution Criteria

Resolve when:

- service health checks are green
- service accepts real traffic
- error and timeout signals return to normal
- no new service-down signals occur
- monitoring confirms sustained recovery

Recommended minimum observation window:

```text
10-15 minutes
```

---

## Post-Incident Follow-Up

Document:

- outage start and end
- root cause
- detection time
- recovery time
- user impact
- failed safeguards
- prevention plan

Potential improvements:

- heartbeat signals
- readiness/liveness checks
- automated rollback
- better startup validation
- dependency readiness checks
- service-level objective tracking
